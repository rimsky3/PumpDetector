# Pump Detector — контекст проєкту

Пет-проєкт для портфоліо (перехід у ML/DS): модель, що розпізнає pump-and-dump на крипто-ф'ючерсах
і узагальнюється на тікери, яких не бачила під час навчання.

- Повне ТЗ: https://claude.ai/code/artifact/ced9c93e-7099-4097-934a-4d64159cd413
- Макет інтерфейсу: https://claude.ai/artifact/MAivAWzKcz2NKqPQs4JENJ

## Скоуп v1
- Тільки режим Midterm, гранулярність 1h. Shortterm (5m) і ієрархічна схема — у v2.
- Класифікація: 1 = памп триває, 0 = звичайний ринок. Не регресія ціни.
- Код пишеться і запускається локально (Windows, VS Code, Python venv, PostgreSQL).
  Сервер (Vultr VPS, Docker Compose) — пізніше, для скринера 24/7 і публічного демо.

## Дані
- Джерело: Coinalyze API (ключ у `.env`), ліміт 40 викликів/хв, кожен символ у запиті = 1 виклик.
- Біржі: Binance, Bybit, OKX, Aster, Hyperliquid, MEXC. Агрегацію між біржами робимо самі.
- Беремо 60 днів 1h-історії (`--days` за замовчуванням), довше не потрібно.
  Coinalyze зберігає OI ≈ 63 дні, решту ≈ 90 днів; 5m ≈ тиждень.
- Список тікерів — `tickers.txt` (один на рядок); `python fetch.py` без аргументів бере його,
  `--new` — лише тікери, яких ще немає в `markets`. Ліміт рахується за символами, не за днями:
  новий тікер — `--new`, регулярне оновлення всіх — без прапорця.
- Покриття бірж неповне: Aster без OI/ліквідацій, OKX без predicted funding і L/S; для AKE/LSK/MYX/G
  Hyperliquid і MEXC не знайдено. Години без ліквідацій відсутні в таблиці → у ознаках це 0.
- OI і ліквідації тягнемо в USD (convert_to_usd). Обсяг OHLCV буває в монетах або USD —
  див. `markets.volume_denominated`, приводити до однієї одиниці в `features.py`.
- Сховище: PostgreSQL, схема в `schema.sql`. Сирі таблиці: upsert по (symbol, interval, ts).

## Ознаки
OI (дельта, швидкість зміни), OHLCV (log-return, volume z-score, bv/v), funding і predicted funding,
ліквідації (обсяг, асиметрія long/short), long/short ratio.
Усі ознаки відносні до власної історії тікера (z-score, ratio, %), не абсолютні.
`features.py` — один модуль для тренування, інференсу і скринера, без копій логіки.

## Розмітка
- `pumps.csv` (джерело істини) → `python load_pumps.py` → таблиця `pumps` (перезаписується повністю).
  Колонки: base_asset, start_ts, end_ts, pattern_type (pump / false_start / other), notes.
  Часи UTC, "YYYY-MM-DD HH:MM", час відкриття бару; end_ts у CSV — останній бар включно,
  у БД зберігається як виключна межа (+1 год). Для навчання: pump = 1, false_start = 0 (мітку зберігаємо для аналізу помилок).
- Початок: OI стійко зростає над звичайним рівнем (довга передфаза не обов'язкова).
- Кінець: різкий обвал OI після піку ціни.
- Приклади v1: LSKUSDT, GUSDT (був фальстарт без OI — цінний негативний приклад), MYXUSDT, AKEUSDT.

## Модель і валідація
- Baseline: просте правило (OI + volume) → Logistic Regression → LightGBM.
- Дисбаланс класів: class weights або SMOTE.
- Leave-ticker-out валідація; метрики precision / recall / F1, не accuracy.
- Модель мусить перевершити просте правило, інакше це чесний негативний результат.

## Вихід з позиції
- Стоп: 75-й перцентиль MAE в одиницях NATR.
- Основний вихід: ймовірність моделі нижче порогу 2–3 бари поспіль (очікуваний лаг відносно піку).
- Trailing stop (≈1.5 NATR від максимуму) — страховка.

## Структура
- `schema.sql`, `fetch.py` — готові
- Локальне оточення: `.venv` (Python 3.14, залежності встановлені), PostgreSQL — у Docker
  (`docker-compose.yml`, schema.sql підхоплюється автоматично при першому старті).
  Docker disk image — на `D:\Docker` (диск C: майже повний, туди нічого великого не класти).
  2026-09-29: зібрано AKE, LSK, MYX, G (пробно за 90 днів, в БД є рядки старші за 60 днів).
- 2026-09-29: розмічено 6 тікерів (AIN, AKE, G, LSK, MYX, QNT): 10 pump, 8 false_start, ≈270 год класу 1 (~3%).
- Розмітка: `python label.py` — локальний сервер (stdlib http.server, 127.0.0.1:8765) + `tools/label.html`
  (графік — Lightweight Charts з app/vendor, як у дашборді: свічки, клік по свічці = межа інтервалу);
  графіки з БД, кожна зміна одразу пишеться в pumps.csv і синхронізується з таблицею pumps.
  Спільна логіка читання/запису/перевірки CSV — у `load_pumps.py`.
- `features.py` готовий (24 ознаки, таблиця `features`, перевірено на відсутність lookahead); опис — docs/features.md.
- `train.py` готовий: rule / logreg / lightgbm, leave-ticker-out + вкладений вибір порогу, метрики по годинах і подіях;
  звіт reports/train_report.md, OOF-передбачення reports/oof_predictions.csv; опис — docs/modeling.md.
  Перші результати (8 тікерів, 17 пампів): F1 rule 0.55, logreg 0.70, lightgbm 0.72 — моделі > правила, logreg ≈ lightgbm.
- Перегляд помилок: label.py читає reports/oof_predictions.csv — 4-та панель «Модель» (ймовірність, поріг, смужка tp/fp/fs/fn),
  вибір моделі, список помилок по тікеру з переходом; помилки рахуються за поточним pumps.csv. `#TICKER` в адресі відкриває тікер.
- Скринер (каркас): train.py зберігає models/{logreg,lightgbm}.joblib (модель+поріг з OOF+ознаки+data_end);
  screener.py (--loop щогодини о HH:05, --no-fetch) → fetch.collect() для watchlist.txt за 10 днів → features.build()
  → обидві моделі → таблиця signals (in_sample / live, ON CONFLICT DO NOTHING). Опис — docs/screener.md.
  features.py за замовчуванням лише tickers.txt: watchlist-тікери в базі не розмічені й не мають потрапляти в навчання.
- Дашборд за макетом «Pump Detector App» (https://claude.ai/artifact/MAivAWzKcz2NKqPQs4JENJ, екрани Прогноз і Скринер):
  `python dashboard.py` (stdlib-сервер, 127.0.0.1:8766) + `app/dashboard.html`, темна тема з макету. Streamlit прибрано — власник його не хоче.
  Графік — TradingView Lightweight Charts v5 (локально app/vendor/, роут /vendor/): свічки, зони сигналу, мітки угод, панелі OI/обсяг/ймовірність.
  Кнопка «Прогнозувати» = collect() одного тікера (лише якщо в базі немає останньої години) + screener.score_bases().
- Дашборд v2 (макет «Прогноз v2» / «Журнал» на тому ж полотні): три колонки — ліва (модель, P з порогом, метрики, позиція),
  графік, права (список тікерів: пошук, фільтри, ★ у localStorage, сорт P/ΔOI 24г/24 год, спарклайн P 24 год).
  ↑/↓/Enter/F, сповіщення (звук + Notification) лише для нових live-епізодів, поки сторінка відкрита. «?» біля кожного блоку.
  Вкладку «Скринер» прибрано → «Журнал»: journal.py (перша оцінка кожної години серед версій; угоди за risk.py на P/поріг;
  результат: розмітка > автоправило 24 год/+15% ціна/+20% OI > «очікує»). API: /api/list, /api/journal (кеш), /api/meta+screener.
  screener.py пише reports/screener_status.json (виклики Coinalyze, 429, stale/missing, помилки). Статус: Alert ≥ поріг, Кандидат ≥ ½ порогу.
- Ризик: `risk.py` — ATR(14) Уайлдера; стоп = entry − k·ATR, k = 75-й перцентиль MAE пампів (до піку) у NATR,
  рахує train.py і зберігає в bundle['risk'] (зараз k ≈ 2.9); trailing = max high − 1.5·ATR; вихід — 2 бари поспіль нижче порогу.
- 2026-09-29: додано SOON; ZEC прибрано з навчання (багатоденний тренд великої монети, 49% годин пампу, валив F1 до 0.56) —
  скоуп: дрібні перпи. На 9 тікерах / 19 пампах: F1 rule 0.57, logreg 0.64, lightgbm 0.71. Шум між перезапусками ±0.02–0.03.
- OI у монетах: Coinalyze множить усю годинну свічку OI на close години → USD-OI стрибає між годинами з ціною.
  features.aggregate ділить на close свого контракту (oi_coins_*; розриви ~0.01%). Графіки label/dashboard — OI свічками
  в монетах (у label перемикач USD). Експеримент experiments/oi_coins.py: монетні ознаки гірші (LightGBM F1 0.68→0.62,
  шорт-сквіз: ціна ↑, монетний OI ↓) — модель лишається на USD (FEATURES), монетні лише в таблиці (ALL_FEATURES).
- Telegram-сповіщення — окремим кроком пізніше.
- далі: більше розмічених тікерів; метрики ранньої фази пампу (ret_24h домінує — модель частково «бачить, що вже виросло»);
  Telegram; деплой на VPS (Docker Compose: база + screener --loop + dashboard).
